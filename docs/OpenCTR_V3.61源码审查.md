# OpenCTR H60 V3.61 下位机源码审查

审查日期：2026-09-06  
源码包：`OpenCTR_H60V36_R750ROS_V3.61.0602.zip`  
解压目录：`firmware/vendor/OpenCTR_H60V36_R750ROS_V3.61.0602/`

## 结论

这份源码可以解释当前 Type-C 下位机在 230400 8N1 下输出的旧版 X-Protocol
数据，也能作为 ROS 2 串口接入和底盘运动学的参考基线。它不能直接视为
《家庭服务机器人技术方案》中的正式下位机实现，也不满足当前实车自动运动的安全
准入条件。

当前必须保持 `hr_bridge.command_output_enabled=false`。原因是固件接收一次非零速度后
会持续使用最后一个目标值，源码中没有上位机命令超时清零逻辑，也没有找到实际启用
独立看门狗的代码。USB 线松动、上位机崩溃或 ROS 进程退出时，下位机自身不能保证停车。

本次只解压、读取和比对源码；没有改动 vendor 源码，没有写串口命令，没有编译或刷写
固件，也没有启动电机。

## 与当前实机串口的对应关系

源码在 `Robot/main.c` 中配置：

| 接口 | 用途 | 波特率 |
|---|---|---:|
| UART1 | 调试串口 | 230400 |
| UART2 | ROS USB 串口 | 230400 |
| UART3 | 蓝牙 | 115200 |
| UART4 | ROS TTL 串口 | 230400 |

UART2 和 UART4 都采用 X-Protocol：

```text
AA 55 | frame_length | frame_id | payload | uint8累加校验和
```

长度字段包含整帧，16 位数值使用大端序。

| 方向 | 帧码 | 总长度 | 数据 |
|---|---:|---:|---|
| 下位机 → 上位机 | `0x10` | 25 B | accel[3]、gyro[3]、vx/vy/wz、battery，均为 16 位 |
| 上位机 → 下位机 | `0x50` | 11 B | vx、vy、wz，均为有符号 16 位大端整数 |

源码注明速度整数放大 1000 倍，即 `vx/vy` 为 mm/s，`wz` 为 mrad/s。当前实机
连续 10 秒收到 501 个校验正确的 `AA 55 19 10` 帧，约 50.1 Hz；长度、帧码、字段
排列、静止速度和电池数值均与源码一致。这是高度一致的协议证据，但仅凭上行帧仍不能
证明实机烧录的二进制与压缩包内 HEX 完全相同。

## 控制和安全审查

源码中的关键行为如下：

1. `Robot_Task` 每 20 ms 运行一次，即 50 Hz，执行运动学、PID、电机输出和状态上报。
2. `ax_robot_move_enable` 上电默认值为 1。
3. UART2/UART4 收到任意校验正确帧后把控制模式切为 `CTL_ROS`；`0x50` 帧直接覆盖
   `R_Vel.TG_IX/TG_IY/TG_IW`。
4. 目标速度仅做绝对限幅：`vx=1.5 m/s`、`vy=1.2 m/s`、`wz=6.28 rad/s`。没有看到
   加减速斜坡、上位机心跳、命令序号、命令时间戳或命令新鲜度检查。
5. 没有接收超时后把目标速度归零的路径。最后一个非零目标会继续参与 50 Hz 控制。
6. 工程包含 STM32 IWDG 头文件，但未找到初始化、喂狗或任务存活门实现。
7. 低电压保护会停止电机并挂起任务，但不能替代通信断链保护或硬件急停。
8. X-Protocol 只有 8 位累加和，没有正式方案要求的 CRC、协议版本、序号、时间戳、
   安全许可、控制源、故障码和看门狗状态。
9. USB、TTL 和 CAN 均可直接覆盖同一目标速度；没有正式方案要求的单一仲裁状态机。

`hr_bridge` 当前会在 ROS 命令超过 250 ms 后改发零速，并在正常退出时尝试发送零速。
这只能覆盖上位机进程正常运行且串口仍连通的情况，不能弥补下位机自身缺少断链停车。

## 与正式技术方案的关系

正式技术方案保持不变。两者存在以下结构差异：

| 项目 | OpenCTR V3.61 vendor 工程 | 正式技术方案 |
|---|---|---|
| MCU/板卡 | OpenCTR H60 V3.6，STM32F407VET6 | 大疆 C 板，STM32F407IGT6 |
| 底盘默认值 | 麦克纳姆轮 | 四轮差速，`vy` 禁用 |
| IMU | QMI8658A，4 g/512 dps | BMI088 + IST8310 |
| 电机接口 | PWM 直流电机和编码器 | CAN → C620 → M3508 |
| 常驻任务 | Robot/Key/Light/Disp/Trivia 等 | monitor/chassis/imu/command 四任务 |
| 安全 | 低压保护，未见通信超时和 IWDG 门控 | 急停、仲裁、命令超时、任务心跳、IWDG 门控 |
| 协议 | 旧 X-Protocol `0x50/0x10` | 待冻结的版本化 CRC 协议 |

因此 vendor 工程保存在 `firmware/vendor/` 下，作为只读参考和当前硬件临时兼容依据；
正式下位机仍需按技术方案单独实现和验收。

## 后续最小步骤

1. 核对实物控制器丝印、MCU 型号、底盘轮型、电机接口以及急停方式，确认当前接入的究竟
   是 OpenCTR H60 还是技术方案中的大疆 C 板。
2. 在不接电机或车轮悬空条件下做一次只读轮向/编码器检查，确认固件默认 `ROBOT_MEC`
   是否与实物一致；车型不一致时禁止运动。
3. 若短期继续使用 OpenCTR，先在其独立开发分支加入 100–200 ms 通信超时归零、上电
   默认禁止运动、显式使能、速度斜坡、控制源状态和 IWDG 门控，并做台架故障注入。
4. 固件改造通过后，再让 `hr_bridge` 进行“零命令 → 极低速短脉冲 → 零命令”台架测试，
   同时保留物理断电手段。不能用当前 vendor HEX 直接进行 ROS 自动运动。
5. 正式阶段按技术方案实现 C 板四任务和新协议；旧 `0x50/0x10` 仅用于过渡兼容。
