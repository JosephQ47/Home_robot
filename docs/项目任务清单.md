当前载体：PC/Ubuntu 虚拟机临时代替 RK3588；正式方案仍使用 RK3588。

## 状态规则

| 状态 | 含义 |
|---|---|
| 已实测 | 已在当前硬件或真实数据上保存验证结果 |
| 框架完成 | 接口、包、配置或 Mock 可构建运行，尚未完成实机验收 |
| 待实施 | 前置条件具备但尚未开发 |
| 阻塞 | 缺少硬件、参数、协议或依赖，禁止用猜测值继续 |

## 当前安全边界

- Mock 模式只运行 ROS 节点，不打开 STM32、HMMD、相机或雷达设备，不发布速度。
- `robot_bringup.launch.py` 的 STM32 串口、命令输出和 HMMD 串口默认均为关闭。
- 不启动底盘运动，不烧录 Hi3516/STM32，不修改启动分区。
- 未实测的外参、底盘参数、停止区、串口协议和量纲统一保持 `TBD`。

## HMMD 当前替代硬件记录

用户指定当前调试改用微雪 `HMMD-mmWave-Sensor`，正式技术方案原文不修改。官方资料说明该模块为 24 GHz 人体微动/存在传感器，UART 115200、约 100 ms 刷新，提供有人/无人、粗距离和 16 个距离门能量。

框架中的 `hr_hmmd` 发布 `/hmmd/detection`，不会发布 `/scan`。它可用于人体存在确认和粗距离实验，不能提供目标角度、二维地图、通用障碍轮廓或 Collision Monitor 所需平面扫描。因此：

- HMMD 可以成为视觉“检测到人”的辅助确认输入。
- HMMD 距离量纲必须用真实串口帧核对后才能使用。
- SLAM、AMCL、Nav2 障碍物地图、Collision Monitor 和视觉-雷达角度关联仍保持阻塞。

2026-09-06 串口实测：HMMD 接在 CH344 C 路，对应 Ubuntu `/dev/ttyACM2`
（USB interface `04`）；CH344 D 路 `/dev/ttyACM3` 仍为 Hi3516 调试串口。以
115200 读取到固件版本 `v1.6.1`，正常/调试/上报模式命令均返回成功 ACK。当前尚未
收到周期测量帧，需重新上电并在 1 m、2 m、3 m 处进行人体触发和距离量纲标定。
ROS 节点已实测能打开 ACM2，诊断为 `serial open; no report frame received`；底盘与
速度输出保持关闭。

2026-09-06 无地图控制 Mock 实测：向 `/goal_pose` 发布 `odom` 下 0.3 m 目标，
`hr_local_motion` 产生 29 条非零控制，最大线速度 0.10 m/s，随后归零。持续发布
模拟单人目标（2.0 m、0.2 rad）时产生 68 条跟随控制，最大线速度 0.10 m/s、最大
角速度 0.24 rad/s；目标停止上报后自动归零。测试接收端不转发 `/cmd_vel`，未连接
真实底盘。

2026-09-06 重新插拔后枚举：原 CH344 四路 `1a86:55d5` 已从虚拟机断开，因此此前
HMMD `/dev/ttyACM2`、Hi3516 `/dev/ttyACM3` 的映射当前失效。新接入的下位机 Type-C
枚举为 `1a86:55d4 USB Single Serial`，序列号 `5B34018995`，当前设备名
`/dev/ttyACM0`。设备权限为 `root:dialout 0660`，用户 `luckfox` 尚未加入 `dialout`，
所以协议只读采样被权限阻塞；尚未向该端口发送数据。

权限修复并重新枚举后，下位机固定标识为
`/dev/serial/by-id/usb-1a86_USB_Single_Serial_5B34018995-if00`，本次设备名
`/dev/ttyACM0`。230400 8N1 下连续10秒收到 501 个校验正确的
`AA 55 19 10` 状态帧，约 50.1 Hz，与现有旧 X-Protocol 解析器匹配。ROS纯接收
实测 `/wheel/odom_raw` 约 50.4 Hz、速度 `(0,0,0)`、电池约 11.46 V；
`/cmd_vel` 发布者为0，未向下位机发送任何数据。旧帧未包含正式方案要求的安全许可、
看门狗、控制源、序号和时间戳，故 `safety_permit=false`，不能据此启动实车运动。

2026-09-06 收到并审查 `OpenCTR_H60V36_R750ROS_V3.61.0602.zip`。源码确认 USB ROS
串口为 230400、上行 `0x10`、速度命令 `0x50`、50 Hz，与实机上行数据一致。源码同时
确认运动默认使能，且没有找到上位机命令超时清零或实际 IWDG 门控；一次非零命令可能
在通信断开后继续生效。因此继续保持 `command_output_enabled=false`，在完成固件断链停车
改造与台架故障注入前禁止实车 ROS 速度输出。完整证据见
[OpenCTR V3.61 下位机源码审查](OpenCTR_V3.61源码审查.md)。

随后按技术方案新增 `lower/` 下位机验证工程骨架。该代码用于快速验证技术方案，不修改
正式方案，也不视为已完成的量产固件。已实现 CRC-16/CCITT-FALSE、流式
帧解析、序号和时间戳校验、V1 `CMD_MOTION`、150 ms 上位机命令超时、100 ms 遥控
命令超时、遥控接管回中门、安全/任务心跳门、上电心跳准入、故障锁存和显式清除、
差速逆解和速度斜坡。安全许可撤销时立即清除内部速度状态。主机 GCC 严格告警构建、
CTest 和 ASan/UBSan 测试均通过。
协议权威说明位于 [docs/protocol/README.md](protocol/README.md)。板级参数仍为 `TBD`，
所以没有生成或刷写 STM32 固件。

`hr_bridge/home_protocol.py` 已实现同一 V1 帧的 Python 编码和流式解析，共享命令向量
跨 C/Python 校验通过。ROS 节点当前仍使用旧 `0x10` 纯接收路径；在正式 `STATE_FAST`
和 `STATE_SLOW` 载荷冻结并由下位机实现前，不把 V1 发送路径接到真实串口。

资料来源：[微雪 HMMD 官方 Wiki](https://www.waveshare.net/wiki/HMMD-mmWave-Sensor)。
