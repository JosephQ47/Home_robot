## 关键设计点

**底盘全程锁在 ZERO。** 机械臂任务期间 `hr_task_manager` 发布的运动阶段恒为
`ZERO`，于是 `hr_motion_mux` 拒绝一切自动速度源。「机械臂动作时底盘不许动」
由速度链强制执行，而不是靠每个节点各自记得。AC-E2 验的就是这一条。

**`ARM_STOP` 不排队。** 一个需要排在它要停的东西后面的停止不是停止。
准入规则里 `ARM_STOP` 是唯一可以在任务运行中被受理的类型，而且它不占用
active 槽位——那个槽位属于它正在停的任务。

**四类来源统一仲裁。** `SCHEDULE / WEB / VOICE / SYSTEM_BATTERY`，来源不在
白名单直接拒绝（AC-E5）。普通任务不能抢占临界回充。

## 本次修掉的并发缺陷

`hr_task_manager` 用了 `MultiThreadedExecutor`，但**没有给任何回调指定
`ReentrantCallbackGroup`**——所有回调仍落在节点默认的互斥组里，多线程执行器
形同虚设。

后果是：`execute()` 为长任务阻塞时，`/robot_status` 订阅进不来，状态被判过期，
任务把自己中断成 `SAFETY_INVALID`。机械臂任务要跑十几秒，必中；导航任务只要
超过 1 秒也会中。

这正是仓库 CLAUDE.md 那条「不许在回调里阻塞，需要并发就上 MultiThreadedExecutor
+ ReentrantCallbackGroup」——执行器有了，回调组漏了，而只有前者是没有用的。

## 排查过程中值得记的一件事

首轮跑出大量莫名其妙的 `OBJECT_CLASS_UNSUPPORTED` 和 `ARM_GOAL_REJECTED`，
查下来是环境里积了 4 份每个节点：`ros2 run` 会 exec 出子进程，按启动器 PID
kill 杀不掉真正的节点，于是 4 个 `hr_task_manager` 抢同一个 action 名字。

`ros2 node list` 还会因为守护进程的发现缓存继续报已经死掉的节点，
要 `ros2 daemon stop` 才看得到真实状态。验收脚本现在按进程组清理。
